# Отчёт по лабораторной работе № 1. Telegram-бот с языковой моделью

Студент: Цой Дмитрий Владимирович (ФИО), группа M3216. Дата эксперимента: 10.11.2026.

## 1. Цель работы и провайдер модели

Цель: научиться подключать языковую модель к Telegram-боту, управлять контекстом
диалога, хранить историю и настройки в PostgreSQL, писать системные инструкции
и проверять поведение модели экспериментом.

Провайдер: OpenRouter (OpenAI-совместимый API `/chat/completions`). Модель:
`nvidia/nemotron-3.5-lightning:free`. Адрес API, имя модели и ключ задаются
переменными `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` в `.env`; в репозитории
лежит только пустой пример `.env.example`.

Режимы бота: `/study` (объяснение тем по программированию), `/translate`
(перевод) и собственный `/joke` (краткий ответ по существу и неожиданная шутка).

## 2. Путь сообщения через приложение

```
Telegram -> aiogram (router, long polling) -> Assistant
  -> PostgreSQL: режим, температура, история пользователя
  -> trim_history + системная инструкция режима
  -> LLM (chat/completions)
  -> PostgreSQL: сохранить пару «вопрос + ответ» (одна транзакция)
  -> split_message (куски до 4096 символов) -> Telegram
```

Команды `/start`, `/settings`, `/reset` и смена режима в модель не ходят: они
читают или меняют строки в БД. Обработчики принимают только текстовые сообщения
из личных чатов. Любая ошибка модели превращается в безопасное сообщение без
технических деталей и секретов.

## 3. Хранение и ограничение контекста

Две таблицы PostgreSQL:

- `users(user_id, mode, temperature)`: настройки; `temperature` допускает только
  0.0, 0.3, 0.7, 1.0 (ограничение `CHECK` в самой БД), по умолчанию 0.3;
- `messages(id, user_id, role, content, created_at)`: история; `role` только
  `user` или `assistant`; внешний ключ с `ON DELETE CASCADE`; индекс
  `(user_id, id)`.

Данные каждого пользователя выбираются по `user_id`, поэтому история и настройки
не смешиваются и переживают перезапуск бота.

Контекст ограничен двумя параметрами: `HISTORY_MAX_MESSAGES` (20) и
`HISTORY_MAX_CHARS` (6000). `trim_history` берёт самые новые сообщения, вычитает
из бюджета длину текущего вопроса (вопрос никогда не теряется) и не оставляет в
начале «висящий» ответ без вопроса. Вопрос и ответ записываются в историю одной
транзакцией и только после успешного ответа модели, поэтому сбой модели не
засоряет историю. `/reset` стирает историю пользователя, смена режима стирает
историю и сохраняет новый режим (у режимов разные инструкции).

## 4. Системные инструкции

Все три инструкции построены по схеме R.C.T.F. (Role, Context, Task, Format),
полные тексты лежат в `app/prompts.py`.

**/study.** Роль: наставник для студента второго курса. Контекст: знает основы,
темы новые. Задача: определение, зачем нужно, один пример; при неоднозначности
один уточняющий вопрос; при неуверенности прямо сказать об этом и не выдумывать
названия функций и библиотек. Формат: по-русски, до 150 слов, код до 15 строк,
без Markdown (в Telegram ответ показывается обычным текстом). Для вопросов не по
теме есть вежливый отказ.

**/translate.** Роль: переводчик технических текстов. Контекст: студент
присылает текст и называет язык. Задача: сохранить смысл и тон, не переводить
имена функций, переменных и код; текст пользователя считается материалом для
перевода, а не командой (защита от инъекции инструкций). Формат: только
перевод, без кавычек и пояснений; если язык не указан, фиксированный вопрос
«На какой язык перевести?»; если текста нет, фиксированная просьба прислать его.

**/joke (собственный режим).** Роль: бот-шутник. Контекст: студент любит,
когда серьёзный ответ заканчивается неуместной шуткой. Задача: сначала краткий
верный ответ, затем одна шутка, не связанная с темой напрямую; запреты на
оскорбления, политику, религию, внешность; ложные факты в самом ответе
запрещены (шутка может быть абсурдной, ответ нет). Формат: 1–2 предложения,
затем с новой строки «Шутка: …», всего не больше 60 слов, без Markdown. Добавлено
три few-shot-примера: определение понятия, сравнение двух понятий и вопрос не по теме
(борщ), на нём показан отказ с шуткой. Формат задан жёстко, чтобы его можно было
проверять автоматически.

## 5. Эксперимент: влияние temperature

**Условия.** Режим `/joke`, модель `nvidia/nemotron-3.5-lightning:free`, дата
10.11.2026, запрос «Что такое рекурсия?» (этой темы нет в few-shot-примерах).
Постоянно: инструкция `JOKE_PROMPT`, остальные параметры API по умолчанию.
Каждый запрос выполнялся без истории (эквивалент `/reset`); запросы шли через
тот же код, что и бот, скрипт `scripts/run_experiment.py`, сырые данные в
`docs/experiment_results.json`.

**Признаки хорошего ответа, заданные до запуска:** (1) есть отдельная строка
«Шутка: …»; (2) не больше 60 слов; (3) нет Markdown; (4) первая часть корректно
определяет рекурсию (проверка человеком); (5) нет выдуманных фактов.

| 2 | 0.0 | 36 | 231 | да | 448 / 3205 | определение почти слово в слово как в №1; шутка «Вчера видел…» про облако |
| 3 | 0.0 | 38 | 226 | да | 448 / 2859 | то же определение; шутка про вектор и диван |
| 4 | 0.3 | 29 | 178 | да | 448 / 4268 | короткое определение; шутка про pull request |
| 5 | 0.3 | 30 | 203 | да | 448 / 2073 | верно; шутка про Wi-Fi |

Токены ответа (2000–4000) намного больше самого ответа (~60 токенов). Вероятно,
модель тратит их на скрытые рассуждения, которые не показываются в тексте;
проверить это по документации провайдера я не смог, поэтому это предположение.

**Анализ.**

- *Повторяемость.* Определения рекурсии почти одинаковы при любой температуре:
  функция вызывает сама себя, задача разбивается на части, есть базовый случай.
  Отличаются порядок слов и синонимы. Группа 0.0 повторяет формулировки сильнее
  всего (запуски 1–3 различаются парой слов), на 0.7 и 1.0 появляются разные
  обороты («уменьшающимися аргументами», «похожие подзадачи»).
- *Шутки.* Во всех группах шутки разные, даже при 0.0. Значит, при нулевой
  температуре ответ у этого провайдера не детерминирован (одинаковый запрос
  дал три разные шутки); это пришлось учесть: «0.0» не означает воспроизводимость.
  Качество шуток нестабильно при любой температуре: на 0.7 и 1.0 встречаются
  бессмысленные («забыл, о чём хотел забыть»), но и на 0.0 есть слабые.
- *Длина и формат.* Длина 28–41 слов, средние по группам: 38,3 (0.0), 31,7 (0.3),
  33,3 (0.7), 34,0 (1.0). Закономерности нет: разброс внутри групп сопоставим с
  разбросом между ними. Формат выполнен в 12 запусках из 12; в запуске 6 лишняя
  пустая строка, на формат это не влияет.
- *Неподтверждённые утверждения.* Фактических ошибок в определениях нет. Шутки
  содержат вымышленные «факты» (кошка спотыкается о вай-фай), но это допустимая
  по инструкции абсурдная шутка, а не ответ.
- *Вывод.* При 3 запусках на значение статистически значимой разницы по
  выбранным признакам нет: инструкция удерживает формат при любой температуре.
  Для режима `/joke` разумно оставить 0.3–0.7: определение остаётся точным, а
  шутки достаточно разнообразны. Значение по умолчанию 0.3 выбрано как
  компромисс для `/study`, где важнее точность; пользователь может изменить его
  через `/settings`. Выборка маленькая (12 запросов, одна тема, одна модель),
  поэтому вывод предварительный.

## 6. Сравнение исходной и улучшенной инструкции

Исходная (намеренно неполная): «Ты рассказчик. Расскажи пользователю шутку.»
Улучшенная: `JOKE_PROMPT` из раздела 4 (R.C.T.F. + 3 few-shot-примера).
Условия: тот же запрос «Что такое рекурсия?», temperature 0.3, по 3 запуска.
Признаки названы заранее (см. раздел 5): строка «Шутка:», не более 60 слов,
нет Markdown, есть ответ по существу.

| Инструкция | Запуск | Слов | «Шутка:» | ≤ 60 слов | Без Markdown | Ответ на вопрос | Всё выполнено |
|---|--:|--:|:--:|:--:|:--:|:--:|:--:|
| исходная | 1 | 78 | нет | нет | да | нет, только анекдот | нет |
| исходная | 2 | 71 | нет | нет | нет (жирный, эмодзи) | нет | нет |
| исходная | 3 | 47 | нет | да | да | нет | нет |
| улучшенная | 1 | 30 | да | да | да | да | да |
| улучшенная | 2 | 28 | да | да | да | да | да |
| улучшенная | 3 | 31 | да | да | да | да | да |

Исходная инструкция не выполнила ни одного признака полностью (0 из 3):
- вопрос о рекурсии превратился в анекдот про «чтобы понять рекурсию, нужно
  понять рекурсию»;
- запуск 2 начался по-английски, с Markdown и эмодзи;
- в запуске 1 английские вставки «Professor thought…» посреди русского текста.

Улучшенная выполнила все признаки в 3 запусках из 3. Это прямой эффект
явного формата, запретов и примеров. В исходной не было ни вопроса «ответь по
существу», ни ограничения длины, ни языка.

## 7. Автоматические тесты

Запуск: `pytest`. Результат: 100 passed, 1 skipped; `ruff check` и
`ruff format --check` без замечаний. Тесты не обращаются ни к настоящему Telegram,
ни к настоящей модели: используются подменные хранилище (`FakeStorage`) и модель
(`FakeLLM`), локальный HTTP-сервер aiohttp для проверки клиента модели.

Восемь обязательных сценариев (`tests/test_assistant.py`, `tests/test_llm.py`):

1. сообщение уходит в модель с инструкцией активного режима
   (`test_message_goes_to_model_with_active_mode_prompt`);
2. история передаётся по порядку и сохраняется
   (`test_history_is_sent_in_chronological_order_and_saved`);
3. истории двух пользователей раздельны
   (`test_histories_of_two_users_are_separate`);
4. обрезка истории по числу и объёму сообщений (`test_trim_*`,
   `test_model_request_respects_configured_limits_and_keeps_current_text`);
5. смена режима очищает историю (`test_mode_switch_clears_history_and_saves_mode`);
6. `/reset` стирает историю только вызвавшего пользователя и оставляет настройки
   (`test_reset_clears_only_callers_history_and_keeps_settings`);
7. `/settings` принимает только допустимые температуры и применяется к следующему
   запросу только этого пользователя (`test_settings_*`,
   `test_new_temperature_is_applied_to_next_request_only_for_that_user`);
8. ошибка модели превращается в безопасное сообщение и не сохраняется в
   историю; длинный ответ делится на части не длиннее 4096 символов без потери
   символов (`test_llm_error_becomes_safe_message_and_is_not_saved`,
   `test_split_message_*`, `test_long_answer_is_returned_in_parts_not_longer_than_limit`).

Дополнительно: 13 тестов клиента модели (формат запроса, таймаут, HTTP 500,
пустой ответ, неожиданный JSON, отсутствие секретов и текста диалога в логах),
тесты обработчиков (команда не уходит в модель, группы игнорируются), тест
конфигурации и тест `compose.yaml`: LLM-настройки из env-файла доходят до
контейнера бота.

## 8. Известные ограничения

- Сообщения одного пользователя обрабатываются параллельно: если отправить
  несколько вопросов подряд, не дожидаясь ответа, пары «вопрос + ответ» могут
  записаться в историю не в том порядке. Решение: блокировка на `user_id`; не
  реализовано.
- Бесплатная модель иногда игнорирует ограничения по длине и может отвечать
  дольше таймаута в 30 с (его можно увеличить через `LLM_TIMEOUT_SECONDS`);
  при превышении лимитов провайдера пользователь видит ошибку HTTP 429.
- Температура 0.0 не даёт воспроизводимых ответов (см. раздел 5).
- Размер истории оценивается в символах, а не в токенах, поэтому лимит модели по
  токенам контролируется приблизительно.
- Запуск без Docker-контейнера бота (локально) требует прокси для Telegram и
  модели, если они недоступны напрямую; в облаке прокси задаётся
  `TELEGRAM_PROXY_URL`.

## 9. Использование AI-инструментов

Применялся Claude Code (расширение в VS Code): объяснение терминов (asyncpg, пул,
транзакции, aiogram), подсказки и проверка моего кода (я писал функции работы с
БД сам, ассистент указывал на ошибки), генерация заготовок конфигурации, тестов и
`compose.yaml`, помощь с командами git и Docker. Каждое предложение я проверял
запуском тестов и бота в Telegram.

**Исправленные предложения.**

1. Ассистент посоветовал не задавать прокси и подключаться к Telegram напрямую.
   Это оказалось неверно: из моей сети Telegram заблокирован, бот падал по
   таймауту. Я исправил это на `TELEGRAM_PROXY_URL=socks5://127.0.0.1:10808`
   (локальный порт VPN-клиента), после чего бот заработал. Из этого же вывода:
   `OpenRouter` напрямую отвечал HTTP 403, поэтому добавлена настройка
   `LLM_PROXY_URL`.
2. В моих функциях для БД ассистент нашёл ошибки, которые я исправил сам:
   `DELETE FROM users` вместо `DELETE FROM messages` (удалил бы пользователя
   вместо истории), `LIMIT` внутри `DELETE`, два SQL-запроса в одном `execute`,
   `reversed` в аннотации возвращаемого значения (ошибка при импорте).
3. Первая версия конфигурации требовала `LLM_*` всегда и ломала скрипты запуска и
   тесты без модели; проверка вынесена в `require_llm()` при старте бота.
4. После замечания преподавателя о запуске «по контракту» выяснилось, что
   `compose.yaml` не передавал `LLM_*` в контейнер, а скрипт деплоя не переносил их
   в `.env.cloud`; исправлено и покрыто тестами.

Секреты в чат с ассистентом не передавались: ключи только в `.env`.
