# AGENTS.md: правила работы с проектом

Проект: Telegram-бот с языковой моделью (лаба 1), расширенный до агента с
MCP-инструментами (лаба 2). Документы лабы 2: [spec.md](spec.md), [plan.md](plan.md).
Условия лабораторных: [docs/labs-guide.md](docs/labs-guide.md).

## Каталоги

| Путь | Назначение |
|---|---|
| `app/` | приложение: конфигурация, запуск, Telegram-обработчики, логика ассистента |
| `app/handlers/` | тонкие обработчики Telegram: разбирают update, вызывают сервисы, отправляют ответ |
| `app/assistant.py`, `app/llm.py`, `app/prompts.py`, `app/storage.py` | сервис диалога, клиент LLM, инструкции режимов, репозиторий истории (лаба 1) |
| `app/agent/` | (лаба 2) агентный цикл, схемы решений, проверка аргументов, подтверждения, аудит |
| `app/mcp_client.py` | (лаба 2) MCP-клиент: запуск сервера, обнаружение инструментов, вызов |
| `app/mcp_server/` | (лаба 2) MCP-сервер: инструменты `get_weather`, `get_schedule`, `add_reminder`, ресурс |
| `data/schedule.json` | обезличенное учебное расписание (минимум две недели) |
| `docs/evaluation/` | наборы запросов для эксперимента, менять нельзя |
| `scripts/` | запуск, деплой, эксперименты |
| `tests/` | автотесты |

Пометка «(лаба 2)» означает, что модуль относится к лабе 2; статус этапов и
отклонения от первоначального решения записаны в [plan.md](plan.md).

## Команды

Из корня репозитория, с активированным окружением `.venv`:

```bash
python -m pytest
python -m ruff check .
python -m ruff format --check .
```

Локальный запуск (Docker, `.env`) описан в [README.md](README.md). Основная команда
для облака: `docker compose --profile cloud up --build`. Эксперимент лабы 1:
`python -m scripts.run_experiment`. Лаба 2: независимая проверка MCP-сервера
`python -m scripts.mcp_probe`, эксперимент `python -m scripts.eval_routing --version N`;
интеграционные тесты: `RUN_INTEGRATION=1 python -m pytest -m integration` (нужен Docker).

Тесты не обращаются к настоящим Telegram, LLM, погодному API и MCP-серверу: границы
подменяются заглушками. Проверки на реальной PostgreSQL находятся в
`tests/test_integration.py` и по умолчанию пропускаются без доступной БД.

## Переменные окружения

- Любая новая переменная: пустой или вымышленный пример в `.env.example`, чтение и
  проверка в `app/config.py`, передача в контейнер `bot` в `compose.yaml`, строка в
  таблице `README.md`. Тест `tests/test_compose.py` проверяет, что значения из
  env-файла доходят до контейнера.
- Для облака переменные при деплое переносятся из `.env` в `.env.cloud`
  (`scripts/local.py`, `PASSTHROUGH_KEYS`); новые переменные добавляйте и туда.
- `MCP_OWNER_SECRET` при пустом значении генерируется при старте бота (контракт: бот
  поднимается из одних секретов в `.env`). Дочерний процесс MCP-сервера получает
  только свои переменные (`SERVER_ENV_KEYS` в `app/mcp_client.py`), без токена бота и
  ключа LLM.
- Обязательность LLM- и MCP-настроек проверяется при старте бота, а не при загрузке
  настроек: скрипты запуска и тесты должны работать без них.

## Миграции и схема БД

- Схема хранится в коде (`app/storage.py`, `SCHEMA`) и применяется функцией
  `ensure_schema` при старте. Изменения схемы только добавляющие и идемпотентные
  (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`), существующие данные не
  удаляются.
- Ограничения целостности задаются в БД (`CHECK`, `UNIQUE`, внешние ключи), а не только
  в Python.

## Архитектурные границы

1. **Обработчики** (`app/handlers/`) не содержат бизнес-логики, SQL и схем инструментов.
2. **Сервисы** (`Assistant`, агент) работают с хранилищем через интерфейс репозитория
   и с MCP через `mcp_client`; в тестах подменяются.
3. **Репозитории** (`app/storage.py`) единственное место с SQL. Запросы только
   параметризованные.
4. **MCP-сервер** (`app/mcp_server/`) не импортирует код Telegram и агента. Он
   проверяет каждый аргумент сам, потому что схема в описании инструмента не является
   границей безопасности. Исключение из изоляции: чистые функции проверки времени
   (`reminders.py`) и подписи (`owner.py`) используются и ботом.
5. **Модель** получает только список инструментов, обнаруженных через MCP, и историю.
   Она не получает реквизиты БД, пути к файлам и идентификаторы пользователей, а её
   вывод не определяет владельца, пользователя и часовой пояс.
6. **Результат инструмента** это недоверенные данные: он передаётся модели с ролью
   результата инструмента и никогда не меняет правила приложения.

## Безопасность и данные

- Токены, ключи и пароли только в `.env` и `.env.cloud`; они в `.gitignore` и не
  попадают в код, тесты, отчёт, снимки экрана и историю git. Файл окружения целиком
  не передаётся AI-инструментам и не печатается.
- В репозитории нет персональных данных: расписание обезличенное.
- В текстовых логах нет Telegram ID, имён пользователей и текстов сообщений, ключей и
  системных инструкций. Для связи записей используется случайный идентификатор запроса.
  `SecretFilter` (`app/logging_setup.py`) скрывает известные секреты.
- Содержимое строк не выполняется как код, SQL или команда оболочки.
